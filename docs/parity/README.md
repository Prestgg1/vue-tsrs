# `vue-tsc` / `vue-tsrs` parity and performance

## Run against any project

Use Linux with GNU `/usr/bin/time`, and Node.js 22 or newer. Run `npm ci` in the `vue-tsrs` checkout. The target project must already have its dependencies and a local `vue-tsc` installed. Generate framework files first (for example, run `nuxt prepare` for Nuxt).

```sh
node scripts/bench/compare.mjs /path/to/project tsconfig.app.json /path/to/new-results 5
```

Point at a **leaf** config, not a build-mode solution config. Use an output directory that does not exist, outside the checked project. To test a different `vue-tsrs` checkout with dependencies installed, set `VUE_TSRS_ROOT=/path/to/checkout`.

The script invokes each CLI directly via the same Node executable, from the target directory, with `--noEmit -p <leaf-config>`. It runs an untimed config probe, one discarded warm-up per checker, then fresh processes in alternating order. It gives each incremental/composite `vue-tsc` invocation a new build-info path so measurements cannot reuse previous compiler state; writing that state, if applicable, is included. No filesystem caches are flushed. GNU `time` supplies elapsed seconds (`%e`) and maximum resident set size in KiB (`%M`). RSS is the timer's high-water mark, not aggregate memory across concurrent processes. The benchmark includes Node startup, Vue code generation, checking, and diagnostic formatting, but not installs or Nuxt preparation.

Each tool must have stable diagnostics and recognizable exit/output for the run to be comparable. Parity compares a multiset of primary `(relative file, 1-based line, 1-based column, category, TS code)` tuples, including diagnostics without a file. It ignores message text, spans beyond the start, related information and diagnostic order. Exit `0` means tuples matched (even if both tools reported errors), `1` means they differed, and `2` means the comparison was inconclusive or could not run. The output contains raw stdout/stderr and timing files for each invocation, and `report.json` with samples, medians, tuple differences, effective commands, versions, Git state and input hashes.

## Recreate the inputs

The setup script needs Git, npm, gzip and network access. It downloads the upstream sources and restores the exact npm dependency resolutions used for the run, rather than resolving floating package ranges again. The compressed lockfiles are ordinary npm `package-lock.json` files. Installs override the project's checker versions to `vue-tsc@3.2.9` and `typescript@6.0.3`. `--legacy-peer-deps` is needed because the Vite and Simple Sheet `@vue/tsconfig` versions declare TypeScript 5.x peers. These are benchmark installs, not recommendations for upgrading either project.

```sh
work=$(mktemp -d)
bash scripts/bench/setup-projects.sh "$work/projects"
git clone --no-checkout . "$work/checker"
git -C "$work/checker" checkout --detach 01fab38759d37609d22c1c7cad2c3928434ab657
npm --prefix "$work/checker" ci
export VUE_TSRS_ROOT="$work/checker"

node scripts/bench/compare.mjs "$work/projects/vite" tsconfig.app.json "$work/vite-results" 5
node scripts/bench/compare.mjs "$work/projects/sheet" tsconfig.app.json "$work/sheet-results" 5
node scripts/bench/compare.mjs "$work/projects/nuxt" .nuxt/tsconfig.app.json "$work/nuxt-results" 5

# Optional negative control: add it only after measuring the clean scaffold.
cp scripts/bench/Probe.vue "$work/projects/vite/src/Probe.vue"
node scripts/bench/compare.mjs "$work/projects/vite" tsconfig.app.json "$work/vite-probe-results" 3
```

| Input | Pin | Checked scope |
| --- | --- | --- |
| Vite Vue + TypeScript starter | `create-vite@8.2.0`, Vite `7.3.8` | `tsconfig.app.json` |
| [Simple Sheet](https://github.com/kittors/simple-sheet) | `8def7751e7ce4a74e1b4b260bf01d7e9aa9befcc`, Vite `6.4.6` | `tsconfig.app.json` (app and packages) |
| [Nuxt starter](https://github.com/nuxt/starter) | `13659102e9c35042f8c56e5d9deb3e1bd8c96fac`, Nuxt `4.6.4` | `.nuxt/tsconfig.app.json`, generated by `nuxt prepare` |

## Observations (November 23, 2026)

`vue-tsrs` was measured at `01fab38759d37609d22c1c7cad2c3928434ab657`, with `tsrs@7.1.0-beta.tsrs4`. Both checkers used Vue Language Core `3.2.9`; the fixture projects use Vue `3.5.46`. Measured on one Linux x86-64 laptop (Intel i5-1235U, 15.2 GiB RAM, Node `24.18.0`, npm `11.16.0`). Results are local end-to-end medians, not a controlled compiler microbenchmark.

| Clean project | Diagnostics tsc / tsrs | Wall s tsc / tsrs | Peak RSS KiB tsc / tsrs |
| --- | ---: | ---: | ---: |
| Vite starter | 0 / 0 | 2.95 / 1.99 | 301,240 / 141,060 |
| Simple Sheet | 0 / 0 | 4.52 / 2.28 | 357,072 / 140,404 |
| Nuxt starter | 0 / 0 | 4.25 / 2.97 | 418,864 / 159,176 |

Across these three clean leaf checks, `vue-tsrs` took 30–50% less wall time and used 53–62% less peak RSS. Clean results only show both tools accepted the measured inputs. These fixtures do not establish general parity or benchmark build mode, watch mode, declaration output, or the other generated Nuxt configurations.

The separate Vite negative control matched both expected locations: script `TS2322` at `src/Probe.vue(2,7)` and template `TS2339` at `src/Probe.vue(7,57)`. The checker exits differed (`vue-tsc`: 2; `vue-tsrs`: 1), but both were diagnostic exits and the benchmark returned 0. Three timed samples gave 2.38 s / 269,608 KiB for `vue-tsc` and 1.47 s / 142,188 KiB for `vue-tsrs`.
